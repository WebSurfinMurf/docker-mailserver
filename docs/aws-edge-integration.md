# Running behind the AWS mail-edge

How this `docker-mailserver` (DMS) stack works when its public ports are terminated on an
AWS edge and tunnelled home, instead of being exposed directly. The **AWS half** lives in
[`~/projects/aws/mail-edge/README.md`](/home/administrator/projects/aws/mail-edge/README.md);
read both — they are one system.

## Why this is needed

Home is on **Verizon residential**: inbound 25 is blocked, the IP is dynamic, and it's on the
Spamhaus PBL so outbound mail is rejected. The AWS edge gives us a public Elastic IP with
reverse DNS. DMS stays the **single source of truth** for all mail config; AWS is a dumb pipe.

## The one thing that must change here: PROXY protocol

If the edge just TCP-forwards, DMS would see **every** connection as coming from the edge's
tunnel IP — breaking Rspamd scoring, greylisting, and Fail2ban (they'd all act on one IP).
The fix is **PROXY protocol**: HAProxy on the edge prepends the real client IP, and DMS is
configured to trust and read it. Postfix and Dovecot both support it. [DMS tutorial][dmsproxy]

> ✅ **Applied and verified 2026-07-28** against DMS v15.x. The upstream tutorial's exact
> directives needed adjusting for this deployment (below) — there's still an open request to
> make this env-var-driven ([#3866][iss]) that may simplify it in a future DMS release.

### Postfix — `config/postfix-master.cf` only (deliberately not `postfix-main.cf`)

- `smtp/inet/postscreen_upstream_proxy_protocol=haproxy` (port 25, fronted by `postscreen`)
- `submission/inet/smtpd_upstream_proxy_protocol=haproxy` (port 587)
- `submissions/inet/smtpd_upstream_proxy_protocol=haproxy` (port 465 — DMS calls this listener
  `submissions`, not `smtps`)

Deliberately **not** set globally in `postfix-main.cf`: that would also apply to the internal
127.0.0.1 amavis reinjection listener, which will never receive a PROXY header and would
break local delivery. Scoping per-listener in `postfix-master.cf` avoids that.

### Dovecot — `config/dovecot.cf`

- `haproxy_trusted_networks = 10.77.0.1/32` — trust ONLY the edge's tunnel IP; a wider CIDR
  would let anything else reaching 993 spoof its source via a forged PROXY header.
- `haproxy_timeout = 3 secs`
- `service imap-login { inet_listener imaps { haproxy = yes } }` — only the `imaps` (993)
  listener is proxied. Plain `imap` (143) doesn't need it: it's bound inside the
  `mail-edge-wg` network namespace, unreachable from the LAN or internet.

### The contract with the edge (as built)

There is **no port remapping**. `mailserver` shares `mail-edge-wg`'s network namespace
(`network_mode: service:mail-edge-wg` in `docker-compose.yml`) instead of publishing host
ports, so Postfix/Dovecot bind `25/465/587/993` directly inside that netns — with no
conflict against Traefik, which still owns `0.0.0.0:{25,465,587,993}` on the host for
anything not going through the tunnel.

| Public port (edge) | → home listener | PROXY variant |
|---|---|---|
| 25 (postscreen) | `25` | `send-proxy-v2` |
| 587 submission | `587` | `send-proxy-v2` |
| 465 smtps | `465` | `send-proxy-v2` |
| 993 imaps | `993` | `send-proxy-v2` |

HAProxy on the edge sends `send-proxy-v2` uniformly to all four. Port 143 (plain IMAP) is
**not** proxied or exposed — it stays bound inside the netns, unreachable from the LAN or
internet, so it needs no PROXY listener. Keep this table in lockstep with the `aws/mail-edge`
HAProxy config — it's the seam.

## Network / tunnel

- WireGuard runs as its **own container**, `mail-edge-wg` (`lscr.io/linuxserver/wireguard`),
  not as a host-level `wg-quick@wg0` unit — this host has no passwordless sudo, so an
  autonomous worker cannot install a systemd unit. The container owns the network namespace
  that `mailserver` joins via `network_mode: service:mail-edge-wg`; wg0/10.77.0.2 exists only
  inside that netns. Consequence: restarting `mail-edge-wg` destroys the namespace and
  `mailserver` must be restarted after it — Docker will not cascade that restart on its own.
  A `depends_on: condition: service_healthy` plus a healthcheck that checks for a live `wg0`
  (not just an open port) exists in `docker-compose.yml` to catch that failure mode.
- Home dials **out** to the edge (outbound UDP 51820, not ISP-blocked); the edge can never
  initiate, since home sits behind NAT on a dynamic residential IP. `PersistentKeepalive = 25`
  keeps the NAT mapping open. Peer config lives at
  `~/projects/secrets/mail-edge-wg.conf` (mode 600), generated by `aws/mail-edge`.
- `haproxy_trusted_networks` (Dovecot, `config/dovecot.cf`) is scoped to `10.77.0.1/32` — the
  edge's tunnel IP only. Postfix's proxy directives (`config/postfix-master.cf`) are scoped
  per-listener rather than global, so the internal amavis reinjection listener on 127.0.0.1
  never gets stuck demanding a PROXY header it will never receive.

## Accounts

Mailboxes/domains via **postfixadmin** (already in the compose) or `setup email add`. Nothing
about account management changes under the edge.

## Test plan

1. ✅ **Tunnel up:** `wg show` both ends; ping tunnel IPs — verified bidirectional, survives
   container restart.
2. ⬜ **Receive real external mail:** blocked on the MX cutover (out of scope here).
3. ✅ **Real IP preserved:** confirmed via direct connections to the public edge — Postfix
   (`postscreen`, `submission`, `submissions`) and Dovecot (`imap-login`) logs all show the
   real client IP (`108.35.80.85`), not the tunnel peer (`10.77.0.1`). See log excerpts above.
4. ⬜ **Send to a third party** (`swaks --to you@gmail.com …`): deliberately **not run** — the
   Elastic IP's PTR is still pending, so outbound test mail to real providers risks reputation
   damage before go-live. Test with local/self-directed delivery only until PTR resolves.
5. ⬜ **Deliverability** (mail-tester.com, PTR via `dig -x`): blocked on PTR + MX cutover.
6. ⬜ **Fail2ban bans on real IP, not tunnel IP:** not yet exercised — plausible given IP
   attribution is already correct in the logs above, but not directly tested.

## Current stack state (2026-07-28)

- **Live and verified.** `mail-edge-wg` and `mailserver` are both up and healthy; the tunnel
  passed a bidirectional ping test and survives container restart (`restart: unless-stopped`,
  healthcheck-gated `depends_on`).
- PROXY protocol is configured and confirmed working on all four edge-forwarded ports. Direct
  evidence from `docker logs mailserver`, same day:
  - `postfix/postscreen: CONNECT from [108.35.80.85]:54332 to [10.60.1.79]:25` (port 25)
  - `postfix/submission/smtpd: connect from …fios.verizon.net[108.35.80.85]` (port 587)
  - `postfix/submissions/smtpd: connect from …fios.verizon.net[108.35.80.85]` (port 465)
  - `dovecot: imap-login: … rip=108.35.80.85, lip=10.60.1.79` (port 993)

  In every case the logged address is the real Verizon client IP, not the tunnel peer
  `10.77.0.1` — proof the PROXY header is being read, not just accepted.
- Traefik still owns `0.0.0.0:{25,465,587,993}` on the host for anything reaching it directly;
  it does not conflict with DMS because DMS never publishes those ports to the host — it binds
  them only inside the `mail-edge-wg` network namespace, reachable exclusively via the tunnel.
- **MX for `ai-servicers.com` still points at Cloudflare Email Routing, not this edge.** No
  production mail flows through this path yet — cutting over is a separate, later, human
  decision (DNS changes are explicitly out of scope for the work that built this).
