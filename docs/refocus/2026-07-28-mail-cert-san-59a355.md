# Brief: serve the wildcard cert so mail.ai-servicers.com validates

## Why this branch exists
Nextcloud Mail cannot open IMAP: `mailserver` presents a certificate whose only SAN is
`ai-servicers.com`, so validating clients reject `mail.ai-servicers.com`. The
`projects/nextcloud` session diagnosed the symptom correctly but concluded Traefik's
certificate extraction was faulty. It is not. The dumper writes **both** certificates into
separate directories; `docker-mailserver` simply bind-mounts the wrong one. The fix is one
line here, and Traefik needs no change at all.

## Inherited context
- `traefik-certs-dumper` runs `file --version v3 --domain-subdir --source /traefik/acme.json
  --dest /certs --watch`, producing one directory per certificate.
- Verified contents of that output directory (read-only, via `docker exec` into the dumper):
  - `*.ai-servicers.com/` → `certificate.crt`, `privatekey.key`  ← **the wildcard, what we want**
  - `ai-servicers.com/`   → `certificate.crt`, `privatekey.key`  ← apex-only, what we serve today
  - plus `diagrams.nginx.…`, `registry.gitlab.…`, and `private/letsencrypt.key`
- `acme.json` holds 4 certificates including **separate** `ai-servicers.com` and
  `*.ai-servicers.com` entries. Both are legitimately issued; this is not a mis-issuance.
- `mailserver` is `SSL_TYPE=manual`, `SSL_CERT_PATH=/certs/certificate.crt`,
  `SSL_KEY_PATH=/certs/privatekey.key`. Its certificate bind mount currently targets the
  **`ai-servicers.com`** subdirectory.
- Confirmed served SAN today: `DNS:ai-servicers.com` only. Confirmed wildcard on Traefik's
  `:443`: `DNS:*.ai-servicers.com, DNS:ai-servicers.com`.
- **Gotcha:** the target directory is literally named `*.ai-servicers.com`. A glob character
  in a path. Quote it correctly in YAML and in any shell command, or it will silently expand
  or fail to match.
- **Gotcha:** restarting `mail-edge-wg` kills `mailserver` with exit 128 — `mailserver` uses
  `network_mode: service:mail-edge-wg` and loses the namespace. Recovery is
  `docker compose up -d mailserver`. Restarting `mailserver` alone is safe and is all this
  change needs.
- **MX now points at this server.** Mail is live and no longer forwards to Gmail, so downtime
  during this change is real lost mail, not a lab inconvenience. Keep the restart tight.
- Nextcloud reaches IMAP only through the public `34.194.247.228:993` — its container resolver
  returns the AWS Elastic IP, not the LAN address. The certificate must therefore validate on
  the public path; a LAN-only fix does not help it.
- Ports 25/465/587/993 all mandate PROXY protocol (`haproxy_trusted_networks = 10.77.0.1/32`).
  Port 143 is plain and published LAN-only on `192.168.1.13`. Use 143 for local probes; use the
  edge for the validating probe.

## Open questions / desired deliverables
- Point the certificate bind mount at the wildcard directory and restart `mailserver`.
- Prove the served certificate now covers `mail.ai-servicers.com`.
- Prove a peer-verifying TLS client succeeds against `mail.ai-servicers.com:993` — that is the
  precise condition Nextcloud Mail needs, and the reason this work exists.
- Decide whether to reference the wildcard directory directly or via a stable symlink or an
  `SSL_CERT_PATH` change; pick one and record why. A directory containing a glob character is a
  foot-gun for whoever edits this next.
- Record the change and both gotchas above in `CLAUDE.md`.
